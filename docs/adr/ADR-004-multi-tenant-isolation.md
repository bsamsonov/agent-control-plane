# ADR-004 — Multi-tenant isolation: RLS first, then credentials, then trace context

- **Status:** accepted
- **Date:** 2026-07-31

## Context

Multi-tenancy failures in B2B SaaS are rarely exotic. They are a forgotten `WHERE tenant_id`
in a new endpoint, a background job that runs without a tenant, an admin screen that queries
across tenants "just for support", or a cached client object reused for the wrong customer.

Agentic systems make this worse in two specific ways. Execution is asynchronous and long-lived,
so the tenant must survive a suspend/resume boundary and a process restart rather than living
in a request scope. And the code that issues queries is partly generated by a model, so
"the developer will remember the filter" stops being a defensible assumption.

## Decision

Defence in depth, with the database as the load-bearing layer.

**1. Postgres Row Level Security is the primary control.**
Every tenant-scoped table has `tenant_id` and a policy
`USING (tenant_id = current_setting('app.tenant_id', true)::uuid)` with the matching
`WITH CHECK`. Tables are `FORCE ROW LEVEL SECURITY`. The application connects as `macp_app`,
a role without `BYPASSRLS` and without table ownership.

The critical detail is the failure mode. `current_setting(..., true)` returns NULL when unset,
the predicate evaluates to NULL, and **the query returns zero rows**. A forgotten tenant
context therefore produces an empty result — a loud, obvious bug — rather than a silent
cross-tenant read. Choosing the fail-closed formulation is the whole point; the fail-open
variant (`COALESCE(current_setting(...), tenant_id)`) is exactly the trap this ADR exists to
avoid.

One subtlety, found by the negative test rather than by reading the manual: once
`set_config()` has run on a pooled connection, `current_setting('app.tenant_id', true)`
returns the **empty string** in subsequent transactions, not NULL — and `''::uuid` *raises*
instead of yielding no rows. The predicate is therefore written
`NULLIF(current_setting('app.tenant_id', true), '')::uuid`. Without the `NULLIF` the failure
mode is a runtime error rather than an empty result: still not a leak, but a far worse
diagnostic. This is exactly the class of detail that only a deliberately hostile test finds.

**2. Tenant context is transaction-scoped, never ambient.**
`withTenant(ctx, fn)` opens a transaction, issues `SET LOCAL app.tenant_id = $1`, and hands the
*client* to the callback. `SET LOCAL` dies with the transaction, so a pooled connection cannot
carry a tenant into the next checkout. No module-level "current tenant" variable exists, which
also means async work cannot inherit the wrong one.

**3. Credentials are per-tenant and envelope-encrypted.**
`tenant_credentials` holds AES-256-GCM blobs; the DEK is wrapped with a master key from the
environment. MCP clients are cached per `(tenant, server)` — never globally — so a connection
authenticated as tenant A is structurally unable to serve tenant B.

**4. Tenant is part of the trace context, not only the data path.**
`tenant_id` and `run_id` are columns on every audit row, and the audit log is RLS-protected
like everything else, so the trace view a tenant sees is built from its own rows only.
Isolation you cannot observe is isolation you cannot audit; and support requests always
arrive as "what happened for this customer", which must be answerable without a cross-tenant
query. When OpenTelemetry is added, the same two values become attributes on every span —
not wired in this POC.

**Rejected: database-per-tenant.** Correct for a handful of large enterprise customers and the
right answer if a customer contractually requires it. Rejected here because migration and
connection-pool management costs scale linearly with tenant count, and the POC's point is the
policy layer, not the storage topology. `docs/SCALE-LIMITS.md` covers the hybrid path.

**Rejected: application-level filtering only.** This is the status quo that produces the bugs
listed above. Kept as a *secondary* layer — repos still scope explicitly — but never as the
only one.

## Consequences

**Positive**

- The isolation guarantee is enforced by a component that has no bugs of ours in it.
- The negative test is cheap and unambiguous: query without a tenant setting, assert zero rows.
  It is a required test, not an optional one.
- Support tooling must adopt an explicit "act as tenant X" ceremony, which is itself auditable.

**Negative**

- Every connection checkout costs an extra `SET LOCAL` round trip inside the transaction.
- RLS predicates are invisible in query plans until you look for them; a missing index on
  `tenant_id` degrades quietly. Composite indexes lead with `tenant_id` for this reason.
- Migrations and seeding need an admin role that bypasses RLS — a deliberately separate
  connection string, never the one the app uses.
- Cross-tenant analytics (usage reporting, billing) needs its own path and its own review.
  That path does not exist in the POC, which is the honest answer for its scope.

## Verification

`packages/db/test/rls.test.ts` asserts: acme sees only acme rows; writing a foreign
`tenant_id` raises a `WITH CHECK` violation; an unset context returns zero rows; and the
setting does not survive into the next pool checkout.
